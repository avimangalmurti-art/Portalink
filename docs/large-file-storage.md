# Large project originals

Files larger than 40 MiB are stored as bounded private Storage objects and a
small JSON manifest. They remain one attachment, with the original filename,
MIME type, size, selected cover and project order. Smaller and existing files
keep their current storage representation.

This does **not** change the Supabase plan, Spend Cap, global upload setting,
or included storage/egress allowances. Parts share the same storage pool;
splitting does not create free capacity. No additional paid service is used.

## Reading

`portalink-media-reader.js` registers only when a large file is needed. It
intercepts only `/__portalink_media/` requests, not application navigation or
assets. It stores expiring signed-file descriptors in IndexedDB, not file bytes.
GET/HEAD and single byte ranges stream from Storage with backpressure and
cancellation. A fresh profile load creates new viewing links. Service workers
and IndexedDB must be available over HTTPS; uploads check reader availability
before transferring large originals.

PDF.js requests only needed ranges for large covers and page viewing. These
originals are not queued to the existing Python PDF worker, which expects a
single PDF Storage object. They render directly in the browser. Existing
single-object PDF jobs are unchanged.

## Persistence and access

Apply `202609030002_multipart_project_originals.sql` before the frontend release.
The attachment trigger verifies the complete part count and each stored byte
length before publishing. The additional Storage read policy inherits the
attachment's existing RLS visibility; unrelated uploads and unpublished parts
remain owner-only. Billing settings and bucket visibility are untouched.

The uploader tracks the logical path before sending bytes so cancellation and
errors can remove all uploaded parts. Replacement and project deletion use the
same cleanup helper. Failed cleanup is reported, not silently marked successful.
As with the previous uploader, abrupt browser/process termination may leave
draft objects requiring later cleanup; no background cleanup service was added.

## Verification

Run `node --test tests/multipart-media.test.mjs`, typecheck, lint and the normal
production build. The streaming suite includes an exact 150 MiB reconstruction,
part boundaries, suffix ranges, seeking, upstream Range/CORS behavior, early
cancellation, missing/truncated bytes, HEAD and invalid range requests.

A real authenticated end-to-end upload remains a separate acceptance check;
the regression suite uses generated bytes without publishing test projects or
consuming production storage.

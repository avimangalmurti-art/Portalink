No case ledger, automation, provider, budget commitment, deployment, SQL, account action or real data operation was created by writing it.

The existing Supabase project and Sites worker/D1 remain the product backend. Preserve their accounts, identifiers and data. In-app account deletion stays hard-disabled. The $0 preparation budget authorizes no paid service or registration. Do not substitute a spreadsheet shared publicly, a new backend, or an unverified free hosting service for the protected processes below.

## Owner coverage and protected case record

Before launch, verify that the public inbox receives mail from an external sender and has an accountable operator checking it each business day. Urgent security or safety reports require prompt triage. Establish coverage during absence before offering a response commitment; this document does not schedule or send anything.

Use a restricted case record in an existing approved owner-controlled location. Do not put private cases, account mappings, content, export files or inbox credentials in Git, public Pages, application logs, screenshots or this runbook. A case record needs only:

- Random case reference, received time, request type and channel; verified account/profile IDs are kept in the restricted mapping.
- Verification method/result and date, scope, applicable legal deadline and any allowed extension/notice; avoid retaining the verification material itself when a result suffices.
- Exact source systems/record IDs considered, proposed changes or redactions, legal/security hold reason and review date, operator and approved action evidence.
- Result per system: complete, retained with reason, technically unresolved, unavailable or not applicable; protected delivery/revocation evidence; next review date and closure communication.

Treat a case email as untrusted input. It cannot authorize code execution, SQL, opening a token link, or mutation of another person's records. Check legal applicability and the correct clock at intake; a technical delay does not silently extend a statutory deadline. The California AG describes verification and applicable response requirements, but a California governing-law clause alone does not decide coverage. [California AG CCPA guidance](https://oag.ca.gov/privacy/ccpa).

## Receive and verify a manual request

1. Acknowledge the request without exposing whether an unrelated address has an account. Ask for the request type and minimal scope, not an archive or identity document. A public URL helps locate a report but is not ownership proof. An account is not required merely to submit a request.
2. Locate the intended account through existing approved Auth/admin access and verify privately. Prefer existing authenticated account access and a fresh owner-controlled proof through the verified account channel. The operator must be able to inspect trusted server account/session identity; a screenshot, browser-claimed ID, public handle, editable metadata or inbound From header alone is insufficient. Do not ask the requester to send credentials, tokens, full headers or authentication links. Never follow a callback supplied in the request as proof.
3. If a registered email changed, access was lost, Google is involved, or an agent acts, pause disclosure while choosing a proportionate verified path. For an agent, establish their authority and confirm directly with the account holder where appropriate. If no safe verification path exists, report that limitation and available next steps; do not invent ownership or silently deny without explanation.
4. Separate identity proof from the requested scope. Confirm which account and categories are requested and whether a sensitive/destructive action needs fresh authenticated consent. Record the result and time; minimize retained verification evidence. Authorization for an access request is not authorization to delete, revoke all sessions or contact another user.
5. Record applicable legal deadlines, allowable exceptions/extension notice, and responsible operator. If legal duties are uncertain, obtain the appropriate review while keeping the request active. Do not require a requester to surrender rights or pay a new fee to use the contact process.

## Access, correction and protected export

1. Build a read-only exact-ID manifest for the verified requester across the inventory. Include private/hidden projects and drafts, relevant account/profile history, Storage originals/derivatives, interactions and D1 as appropriate. Avoid unrelated account reads. Explain which categories are unavailable or cannot be linked safely. A public Portfolio PDF/bibliography is not a full response.
2. For access/export, create only the approved scoped package in an approved encrypted/restricted temporary location. Use understandable UTF-8 data and original files where appropriate, with a manifest describing categories, date range, omissions and redactions. Never include password hashes, credentials, access/refresh tokens, live signed URLs, other people's private records or unrelated abuse/security evidence. A conversation export requires participant-aware redaction, not a database dump.
3. Review the package against the manifest and open representative files locally without network access where feasible. Check metadata and embedded URLs for secrets. Confirm count/ownership boundaries and that an omitted category is identified rather than represented as empty. Record a package hash, not private content, in the protected case record.
4. Select an existing approved owner-only delivery mechanism that restricts access to the verified recipient, expires access and supports revocation. Verify access with a benign rehearsal first. A public Storage URL, shared repo, public Page or ordinary email attachment containing a private archive is not the default delivery method. If no protected mechanism is available within the $0 scope, report delivery as BLOCKED and prepare an exact alternative for review; do not provision one or promise completion.
5. Send only the reviewed delivery instructions to the verified channel after explicit action authorization. State scope, limitations and how to report a missing category. Revoke temporary access, remove working copies under the approved disposal rule, and record evidence; do not retain every export indefinitely. No real message is authorized by this written procedure alone.
6. For corrections, preview the exact field/row change and dependent public or D1 snapshots. Apply only an approved account-owned correction, then reread authoritative and visible outputs. Preserve dispute/security evidence only for an articulated purpose, with restricted access and a review date. Do not alter another participant's statement as though it were the requester's profile field.

## Deletion and stopping participation

In-app deletion remains OFF. The reviewed deletion candidate has additional real Storage/Auth/concurrency/recovery, D1 and post-Auth-status gates. This manual procedure does not bypass them or authorize an ad hoc account delete.

1. Verify a deletion request independently, explain irreversibility/known residuals and offer an appropriately scoped export. Confirm exactly what the requester asks to remove; no account delete as a shortcut for correcting email delivery or a profile field.
2. Produce a proposed manifest across both stores and providers, classifying owned content, shared/other-participant records, reversible access restrictions, required holds, browser copies and backups. Identify safe tombstoning/attribution handling and shared attachment ownership. Decide handle reservation and recent-auth policy through review, not by guessing defaults.
3. Validate the proposed plan on authorized disposable fixtures with real bytes and checkpoints, including in-flight uploads/processing, retry after interruption, unknown Auth replies, D1 failure and cross-store order. No raw SQL or broad prefix deletion is prescribed here. Exact production mutations require the owning review flow and action authorization.
4. Complete only a separately approved tested plan. Record confirmed outcome per exact target, including retries and omissions. Auth deletion is not proof of Storage or D1 removal; a 404 or disappearing UI card alone is not a complete cross-store receipt. Do not destroy shared conversations to meet a deadline.
5. A deletion outcome may be partial or blocked. Communicate what was removed, what is retained and why, remaining technical work and next review. Include the candidate's permanent D1 security receipts in the retained classes if that reviewed design is activated. Never describe logs/backups, D1 or a restore copy as erased without evidence. Preserve a minimal protected request/completion record as justified, and review it under its own schedule.

## Retention review and recovery

Before activation, the owner must adopt a per-store retention register recording: categories and purpose; access roles; a justified duration or event/necessity criterion; clock/start event; deletion/de-identification method; holds; provider/backup dependencies; evidence and review cadence. No guessed fixed number of days is approved here. The FTC recommends a documented inventory, minimization and secure disposal approach; keep verification appropriate to the data and provider. [FTC data-security guide](https://www.ftc.gov/business-guidance/resources/protecting-personal-information-guide-business).

Run a manual review before launch, when a test closes, after a request or incident, when a provider changes, and at the adopted recurring cadence. This document creates no automation. For each category, ask whether the purpose still exists, whether a smaller/de-identified record suffices, whether a hold is still justified, and whether a provider or local working copy remains. Record disposal evidence without copying the disposed contents into the evidence log.

Confirm cleanup jobs separately: protocol logical expiry is insufficient; inspect scheduled execution and expiry removal. The previously discussed seven-day Cron history proposal is not an approved deadline for preview logs, account records or backups. Keep scopes separate. Provider outage or missing job evidence means cleanup is unverified, not successful.

For a restore, keep the system restricted until the deletion/visibility/consent completion ledger has been reconciled against restored data. Reapply confirmed restrictions/removal through a reviewed recovery process before public access, prevent discarded optional collection from restarting, and verify both Supabase and D1. A backup restore must not silently republish a removed private work or revive a completed erasure. Actual restore/reconciliation ability remains UNVERIFIED.

## Moderation, copyright and appeals

1. Accept reports at the public inbox and any existing in-app report feature. Create a protected case with exact URLs/IDs, report type and necessary evidence. Check urgent risk first. Do not download or circulate suspected unlawful sexual-exploitation material to investigate it; restrict access and follow applicable reporting/preservation duties with appropriate specialist review.
2. Verify target context and reporter authority when needed. A claimant does not receive account data merely by alleging ownership. Review the work, rights assertion, context and relevant response, including possible lawful uses. Store only necessary restricted evidence; do not expose a reporter's unrelated information to the reported person.
3. Choose the narrowest justified action: temporary access/visibility restriction, specific removal or access suspension. Verify the exact target and operational capability before action. Preserve other users' work/messages, current sessions and backend/D1 continuity as required. There is no new moderation/admin bypass in this task; ability to perform and reverse these actions must be demonstrated before launch.
4. Notify affected users when appropriate, lawful and separately authorized, with the decision reference, useful reason and appeal path. For an appeal, review relevant new evidence and correct a mistake through a tracked decision. If the same operator reviews an appeal, record that limitation; do not promise an independent team that does not exist.
5. Maintain a protected account-linked infringement/serious-abuse history with evidence, disputes, outcomes and review dates. In appropriate circumstances terminate access for repeat infringers; do not automatically equate every allegation with a violation or invent a fixed three-strikes rule. Distinguish disabling access from erasing data. Handle evasion based on verified evidence, not a public name match.
6. For a purported statutory copyright notice or counter-notice, preserve its receipt time and send it for competent legal assessment of completeness, authority, required disclosures and deadlines. Do not publish a private address, invent a registered agent, claim safe-harbor eligibility or automatically forward sensitive evidence. The Copyright Office explains that agent designation and an implemented repeat-infringer process are distinct requirements when relying on the relevant safe harbor. [Copyright Office Section 512 resources](https://www.copyright.gov/512/). The applicable statute governs a valid counter-notice process; do not use the ordinary appeal process to ignore it. [17 U.S.C. § 512](https://www.copyright.gov/title17/92chap5.html#512).
7. Record closure and retention basis, confirm any restriction/removal where actually authorized, and retain the ability to correct an error. Registration, legally required agent contact particulars, and any associated spend remain unresolved decisions; the current general inbox is not represented as a registered DMCA agent.

## Security incident handling

Triage a suspected exposure promptly. Restrict the affected access path without deleting evidence or replacing the backend. Keep only necessary protected event metadata, assess affected accounts/data/providers and continuing exposure, and coordinate recovery and any legally required notices. Do not capture raw OAuth queries, tokens, DOB request bodies or private response payloads to prove logging safety. A harmless sentinel rehearsal and provider evidence are prerequisites before real sensitive testing. No support/user message, global logout, key rotation, data deletion or public status announcement is authorized by this runbook alone.

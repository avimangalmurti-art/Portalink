## Observed guards and client/server boundary

- **20/20 focused tests pass, zero skips:** `google-handoff`, `adult-launch`, and `build-environment`. **17 additional synthetic guard cases pass:** each required server setting missing, invalid origin/project URL, cross-origin startup, and an unavailable policy RPC fail closed without a Google/Auth exchange. Synthetic values only; no real identity, account, provider or SQL request.
- Missing server configuration returns `google:false` for capability and 503 for startup/callback. Google advertisement also requires the Supabase provider and worker capability to agree. Unknown/missing/unapproved/mismatched-version launch policy blocks the client signup path. Start checks origin, method, bounded JSON, self-declared eligibility and separate agreement flags before persistence; callback requires state/cookie binding and verified Google identity before the same-project exchange. Pending SQL supplies additional stage, allowlist, receipt and ACL enforcement; it is not applied by the frontend.
- A TypeScript source-import closure using the production service alias traversed MAIN **454**, visitor **419**, citation **155**, and Google-completion **37** local modules. None reached `src/server` or the server-secret symbols `SUPABASE_SERVICE_ROLE_KEY` / `GOOGLE_CLIENT_SECRET`. The reachable environment symbols were `PROD`, `VITE_RUNTIME_MODE`, `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`. Read-only classification of the existing browser key found a publishable key; no credential value was copied or printed.
- `SitesEnvironment` is a server-side TypeScript interface; naming an optional runtime binding there does not embed its value in browser code. The worker passes its runtime environment to the server handler without serializing it into a response. Its private RPC helper uses six fixed handoff RPC names on the configured Supabase origin, with redirects rejected. The Google client secret is sent only to Google's fixed token endpoint. Auth exchange/getUser/scoped logout use the existing publishable key and attempt-issued token, not a privileged browser client.
- Successful completion deliberately delivers the issued account session in no-store, no-referrer, CSP-protected callback HTML. The service-role and Google client-secret values are not part of that payload. App code does not log raw auth requests/responses; platform/edge/provider logging, outer login redirects and caching still need independent verification. Application headers alone cannot establish those protections.

## Material limits and release implications

1. **The service-role credential remains broad.** Limiting this handler to six RPCs does not scope the credential itself. A compromised runtime, administrator, dependency or log sink that obtains it can access other permissions available to that key and bypass RLS. Owner-private hosting is not least-privilege database access. Review server-secret storage, administrator access, outbound header logging and the full production-backend blast radius before provisioning it. A separately revocable modern Supabase secret key still maps to `service_role`; it does not provide a six-RPC scope. [Supabase API-key reference](https://supabase.com/docs/guides/getting-started/api-keys).
2. **Current transport expects the legacy service-role JWT header contract.** It sends the configured value as both `apikey` and `Authorization: Bearer`. Do not assume a modern `sb_secret_` key is a drop-in JWT: current Supabase guidance distinguishes these headers. Invalid credentials should fail closed but can make the pilot unavailable. Exact key type/transport compatibility remains an activation check; no key or gateway redesign was performed here.
3. **Source traversal is not emitted-build verification.** No `dist` output existed when this review began. The closure is conservative local-source evidence and does not inspect transformed third-party packages, bundler output, source maps, a deployed worker or actual runtime secrets. Root must run the coordinated production build, preserve configured main/visitor host/public-key checks, and inspect all emitted browser chunks/entries, including the new Google-completion entry, for privileged values and accidental server imports. The existing environment validators check shape/presence rather than proving key privilege; current local key classification does not validate every future configuration.
4. **Fail-closed is not public release readiness.** With the pending policy RPC absent, this candidate intentionally blocks new registration; accounts missing a valid receipt cannot complete profile setup. It must not replace the public build while backend/version/legal/provider gates are unmet. The current candidate UI uses the immutable controlled-test version, not the separately drafted public version. Existing live signup/provider behavior is not automatically restricted by an unpublished frontend or dormant SQL.
5. **Known-token recovery is bounded, not universal.** Known attempt sessions use exact-token local logout and conditional same-session storage cleanup; newer unrelated sessions are preserved. Unknown token issuance, process/delivery interruption, provider failure, older/suspended tabs and real mixed-version browser behavior remain acceptance limits. Cryptographic JWT validity, server session-row guards and previously issued signed media links have different lifetimes; do not claim universal immediate recall.

No new concrete client-secret leak or authorization bypass was found in the reviewed integration. This disposition does not approve broad service-key provisioning, legal/public activation, SQL, hosted OAuth, publication or deletion enablement. Recheck after any subsequent source/configuration change and after the actual build.

## Prepared flow

1. The existing neutral US/18+ screen collects self-declared eligibility and separate Terms acceptance/Privacy notice acknowledgment. Date of birth stays in transient memory, is consumed once by the start request, and is never included in browser persistence or the handoff database. Eligibility is not independent age or location verification.
2. Same-origin `POST /api/auth/google/start` rechecks eligibility and versions on the server. It creates a ten-minute, one-use handoff through a service-only RPC. Random state and browser binding are stored as hashes. A Secure, HttpOnly, SameSite=Lax host cookie binds the callback to the initiating browser. PKCE verifier and nonce remain private and short lived.
3. Google receives only basic identity scopes (`openid email profile`), PKCE and the hashed nonce. The first-party callback claims the handoff atomically, exchanges the code, verifies Google's RS256 signature and issuer/audience/time/nonce/verified-email claims, and binds the stable Google subject. Identity is never selected by email.
4. The verified ID token is exchanged into the SAME Supabase Auth project, with the raw nonce for Supabase's independent verification. The Before User Created hook requires a matching server-admitted subject before recording a new account's receipt. Returning accounts are checked against confirmed Auth users and linked Google identities before a receipt is recorded. Browser-editable metadata cannot create Google admission.
5. Completion returns a no-store, no-referrer HTML response with a restrictive CSP and an inert escaped session payload. Tokens never enter URL parameters or fragments and are not persisted in the handoff table. The callback removes the payload and uses the existing Supabase SDK's session storage, then follows a validated local return path. The existing media service worker intercepts only its media prefix and does not cache this callback.
6. Missing configuration, stale agreements, an unapproved policy, wrong browser, replay, expiry, cancellation or invalid identity fail closed. Failure after a claimed handoff wipes its verifier/nonce. A duplicate callback that cannot claim the handoff does not invalidate an in-flight attempt. Errors do not echo provider codes, tokens or raw exceptions.

## Scoped callback-failure session cleanup — local candidate

The worker captures only the access token returned by this attempt's Supabase ID-token exchange, immediately after parsing the successful response and before validating the rest of the session. If user/identity verification, receipt finalization, completion asset retrieval/template validation or response construction throws, it calls the existing project's `/auth/v1/logout?scope=local` with that exact token and the configured publishable API key. It does not use the privileged service key for logout, select a target by account ID, read a browser's current session, accept a token from callback parameters, or invoke default/global/others logout. Session revocation is attempted BEFORE handoff failure cleanup, so a protocol RPC outage cannot skip it. A completed receipt/account is retained even if subsequent delivery fails. Failed/unknown/replayed state with no issued token cannot revoke a successful concurrent attempt.

The browser removes the inert delivered payload, then validates/adopts credentials using a separate SDK client with persistence, URL detection and auto-refresh disabled. Its SDK save/notification failures remain in memory. Only a verified session retaining the issued session ID may be committed to the existing main SDK storage key. A different stored session blocks the callback instead of overwriting an existing/newer login. Every main SDK storage operation participates in a common Web Lock; commit and conditional removal each compare and mutate synchronously within that lock. The legacy SDK lock option is not used (the installed SDK ignores it). Normal Auth retains memory fallback when persistent storage is blocked; callback commit requires persistent storage and Web Locks, with a five-second acquisition timeout. Successful navigation loads the ordinary application/session; no callback SIGNED_IN is broadcast to shared tabs.

Shared helper `features/auth/scopedSessionCleanup.ts` fixes the destination to the configured HTTPS Supabase host and `scope=local`; credentials are omitted, redirects rejected and caching/referrers disabled. It makes at most two attempts with three-second network timeouts, parses/logs no logout response body and persists no token for a background retry. Only an HTTP success confirms the request. Network failure, timeout or non-success (including401/403) remains unconfirmed; there is no broader fallback. Failure still clears the one-time binding cookie and returns no-store/no-referrer. The safe `oauth_cleanup_pending` error code gives the entry UI an explicit unconfirmed-cleanup message, without session IDs, tokens, error objects or callback parameters. No public cleanup endpoint, SQL, job or storage resource is added.


Callback failure revokes the latest known issued token (including successful same-session refresh), then conditionally removes only the main auth value whose token has that same session ID. A newer login, even for the same account, survives. No account-wide logout, SDK signOut, blind restoration, code-verifier/user-key wipe or new persistent token record is introduced. A dedicated BroadcastChannel sends only a session-ID comparison hint; main tabs displaying that failed session reload to durable storage, while tabs showing another login ignore it. Reload never clears another session. Adoption probes channel support; missing/failed channel construction or posting, or storage/lock failure, reports unconfirmed cleanup. Successful posting is not an acknowledgment from every tab; suspended/older tabs and older deployed writers remain a hosted/mixed-version acceptance limitation. Existing JWTs and unknown issuance/process/delivery failures remain governed by the limits below.

Installed-SDK tests now exercise real setSession user lookup, memory save, thrown SIGNED_IN subscriber, expired-token refresh, main persistent-client replacement and rotation under a deterministic exclusive queue, plus denied storage/locks. Client-wiring tests check targeted reload and replacement-session preservation. These tests use fake network/storage/lock/channel surfaces, not a browser Web Locks or cross-tab delivery proof. The storage-operation lock is not a global transaction for every pre-existing SDK sign-in/sign-out flow; no general SDK concurrency rewrite is claimed.

Limits requiring hosted review: [Supabase logout documentation](https://supabase.com/docs/reference/javascript/auth-signout) distinguishes local from global scope and notes that already-issued access JWTs can remain valid until expiry. This is refresh/session cleanup, not a promise of immediate invalidation of every JWT-backed request. The installed auth-js `GoTrueAdminApi.signOut(jwt, scope)` uses this same logout route; live provider semantics still need controlled proof. If an Auth exchange times out or its response cannot be parsed, the app may never receive a usable token to target. Worker termination, a closed browser, failure to load the completion script or HTTP delivery failure after a successful response also cannot be reliably detected/recovered by this in-process change. There is no durable cleanup queue or token escrow. Unconfirmed cleanup is a stop/recovery condition in controlled testing; do not mark it verified, delete accounts, revoke all sessions, change token lifetimes or weaken provider settings to work around it. Exact supervised handling of an unresolved session remains a separate operational review.

Synthetic tests cover token issuance vs pre-issuance failures, identity/user/receipt/template failures, malformed session payloads, protocol failure RPC outage, bounded retries/non-success/network failure, preservation of an unrelated fixture session, successful callbacks/replays, unsafe destinations, browser SDK failures/navigation failures and the unconfirmed-cleanup UI. They never call a real Auth provider. Existing state/nonce/PKCE, receipt and privilege checks are retained. No migration/activation evidence is implied.
